# 通讯整体优化方案

状态：整体路线和0.6.0-rc.2草稿交付已确认，源码已实现，交付及实测状态见[开发记录](development-status.md)。全部安装实例须统一安排升级。现行传输方式和计数口径见[通讯流量评估](communication-traffic-assessment.md)，协议以[设计文档](agent-pulse-design.md)为准。

## 目标与已采用方案

保留Go、Rust、Vue以及HTTP/WebSocket，调整业务同步方式为“首次建立基准，之后直接推送变化；正文按事件缓存；断线连续续接，无法续接时重新核对基准”。同时优化Bridge上行、Relay转发、设备保活、管理网页、包下载及流量度量。

日常网络开销应主要由必要保活、新增事件、发生变化的对象和实际阅读内容组成，而不是“历史会话与未读正文总量乘以刷新次数”。所有变更可以一起升级，不建设旧字段适配、双协议长期并行或新旧客户端自动协商平台。

| 可选路线 | 效果与成本 | 结论 |
| --- | --- | --- |
| 仅减少无效刷新、给全量快照加压缩 | 空闲流量明显改善；活跃期间仍反复下载未变化会话和正文，历史越多越贵 | 不作为本次完整方案 |
| 现有HTTP/WebSocket上的对象增量、正文缓存和连续恢复 | 直接消除重复内容；保留现有部署、鉴权和持久化基础，可统一升级全部组件 | 已采用 |
| 更换gRPC、MQTT或通用消息平台，全面改用二进制业务编码 | 仍须实现业务去重、已读/删除变化和恢复；额外框架不能替代这些规则，跨客户端与部署成本更高 | 当前不采用 |

现行实现细节以协议说明和设计文档为准，本页保留已确认的总体范围；实施状态与实际字节测量见开发记录，不将预算视为收益验收。

## 术语

- **基准状态**：某个一致时点的会话摘要、未读标记、来源和必要在线状态。用于首次连接或恢复；不等于全部事件历史及正文。
- **对象增量**：只发送发生变化的对象和相应删除信息，包括会话、未读、来源、设备；适配器报告变化单独通知当前管理页。不会把一条变化放大成整个工作区重传。
- **同步游标**：客户端已成功保存到的服务运行代次与变更位置，用于检查是否漏过变化。不能仅用事件position替代，因为已读、失效、归档和删除不一定新增事件。
- **恢复窗口**：Hub保存的一段有界近期变更，用于短时断线补齐；不是新的权威数据库，也不承诺无限历史回放。
- **可信状态确认**：由Hub核对业务状态并确认客户端已追平的轻量应答；连接心跳只证明链路仍在，不能单独证明任务仍运行。

## 整体改动范围

| 层次 | 当前行为 | 解决的实际问题 |
| --- | --- | --- |
| Tray实时同步 | 初次取得压缩基准；之后由长连接直接发送新增/更新/移除，不再每条changed后GET整份快照，也取消15秒全量下载 | 消除全局快照重复传输和额外请求往返 |
| 订阅范围 | 普通Tray订阅会话、未读和必要来源状态；适配器详情、推送任务和历史分别按页面需要读取/订阅；Bridge只接收自己的在线确认及必要配置变化 | 适配器时间戳和其他管理信息不再广播所有客户端 |
| 正文 | 新提醒完整正文自动取得并缓存；同一事件的后续已读/有效性变化只传小状态；恢复只补本地缺失正文，历史详情按需读取并复用缓存 | 防止长未读正文被每次状态刷新携带；保持通知内容和已缓存离线阅读 |
| 详情视图 | 打开时定位和补齐需要的历史，显示期间接收该会话新增；隐藏时停止额外历史正文拉取，主提醒同步仍继续 | 关闭窗口后不再为不可见历史持续下载 |
| Bridge事件上行 | 复用常驻连接，适度合并短时间事件为小批次；每条事件有独立持久化确认。完成、失败、等待等关键事件及时发送 | 降低大量小HTTP请求和重复头部，不能以丢事件或只保留最后活动减流 |
| Bridge报告与更新 | 安装/运行/错误真正改变时报告，重连补报及低频兜底；在线心跳不携带重复报告。索引仅有变化时下载正文，失败重试与报告周期分开 | 去除10秒重复报告、重复索引下载及弱网重试相互触发 |
| Relay | 新增量与正文语义完整透传；隧道控制信息和原始载荷合理分离，避免正文/ZIP再套Base64。Hub不可达时仍按原范围持久保存事件和已读 | 端到端减流，保留现有离线交付保证；不能变成只在Hub在线时工作的透明代理 |
| 路径恢复 | 保持健康中继连接，在后台探测直连；直连确认可用后切换，失败探测退避，不每30秒主动断开健康连接 | 减少握手、恢复和来源状态抖动；实际切换仍执行现行采集代次规则 |
| 大载荷 | 基准、正文批量、历史等较大JSON使用标准压缩；小增量保持简单编码，已压缩签名包不再次压缩 | 编码优化配合业务增量，不把所有依赖都改为新框架 |
| 包下载 | 仅索引变更时读取新清单；已验证包复用，断链从已保存临时分块续传并最终核验整包摘要 | 手机网络断链不必重复下载整个包；不放宽原公钥、签名或摘要检查 |
| 管理网页 | 使用相同对象变更能力，当前页面订阅对应内容；心跳不再刷新四个全量接口 | 避免将Tray问题转移到浏览器 |
| 统计 | 按进程、路径或消息类别累计应用收发字节、请求或消息次数，Bridge记录上游连接次数；长时比较由采样差值计算 | 将“流量较大”的估计闭合为可验收证据；不记录token、正文、标题或用户输入 |

普通运行事件继续按现行约定保存在Hub。可以合并同一批次内用于界面显示的状态替换，但不能删除原事件、合并关键提醒或改变发生顺序来获取更低流量。通知及时性不依赖用户是否打开详情。

## 不可降低的同步与可靠性保证

### 一致性和恢复

基准与随后增量必须来自同一一致边界，避免“取基准期间发生的事件”落在两者之间。客户端检查增量连续性，成功保存状态和对应游标后才确认；保存失败不推进。已读/提醒失效/归档/主机删除均有明确变化，不能只实现“追加新事件”。

复用Hub已有SQLite作为唯一权威状态，使用有界内存恢复窗口处理短断线。窗口不足、Hub重启、客户端位置不可信时显式重新取得一致基准；客户端继续按事件ID复用已有正文，因此恢复也不必重传全部未读正文。长时间离线的历史正文仍通过既有事件查询取回；基准覆盖全部当前未读事实，不能静默截断。

恢复窗口丢失不等于权威事件丢失。Hub已提交但尚未推送的变更，在重新建基准时仍能反映；需要测试提交、推送、客户端保存和确认各阶段中断。没有当前需求要求增加跨重启的持久增量日志或新的消息服务。

重连时先补交本地未确认已读，再进入可信同步状态，期间暂缓旧提醒。Relay已保存只代表中继暂存；只有Hub确认后客户端才清除待同步已读。正文获取进度与已读事实分开，不因正文暂时缺失就清除未读或假定用户已看过。

### 设备在线、任务状态与唤醒

设备续租、任务状态变化和管理报告分别处理。维持现行35秒失联保护；没有真实任务事件不能靠时间推断任务完成。

Hub进行必要的来源有效性核对后，只向客户端发送小型状态确认。仅当运行代次一致、客户端应用位置已追平、状态保存成功时，才能更新本地可信时间；单纯收到WebSocket pong、Relay存活应答或旧序号不能给过时任务续期。Hub失联、漏增量、缓存恢复或来源过期时仍释放任务唤醒并显示相应未知状态。

来源离线时明确推送状态变化；不向所有Tray广播每次last_seen时间戳。需要精确最近心跳的设备页面按需查询，或基于已有确认计算显示，不以浪费全局数据维持时钟。

### 上行与中继确认

事件仍按event_id幂等，失败重试不换ID，批次中每个事件独立表示已持久接收或拒绝。Bridge原有有界内存队列及停止前排空规则保持，不能把发到socket当作成功交付。

Relay不缓存会话状态冒充Hub，不在Hub离线时生成可信会话心跳；但上行事件和已读暂存能力仍可用。断链前后的重复交付保持去重，实际路径切换遵守collector_id规则，不为节省重连开销恢复不可信的旧运行状态。

## 缓存和新机制的必要性

新增机制仅对应当前问题：有界恢复窗口减少移动网络短断线后的基准重传；事件正文缓存消除相同内容反复下载并保留离线查看；分类型字节统计用于验证实际流量。使用普通数据结构和现有客户端持久化边界，不建设通用发布订阅平台、依赖注入框架或无限增长的日志。

保持现有Hub/Relay数据库和Tray已读/偏好数据，不因协议调整清空它们。正文缓存采用独立、可重建部分；已有未确认已读和提醒去重状态不能以“重建缓存”为由丢弃。若实现确需改变持久结构，先提出明确的数据保留方案，再执行实际迁移或重建；“全部软件都能升级”不代表允许删除数据。

## 升级与版本

本方案涉及Hub、Relay、Bridge、Tray和Web共同更新。此前“现有RC4 Relay可继续转发现有0.6.0首候选”是基于原网络协议未变；不适用于这次整体调整，届时Relay必须同步更新。

已确认在`v0.6.0-rc.2`草稿交付该改动，保留首候选作为比较基准，不公开发布尚未完成验证的修订。Agent原生hook与事件含义原则上保持；适配包是否涨号取决于实际构建内容是否改变，不为追求组件号码一致重建所有包。

全部实例可统一安排一次维护窗口。更新前保存程序/配置及一致性数据，先排空Bridge与中继必要待发，停止会自动同步的旧接入，切换整套候选后逐项确认。当前安装环境不维护旧协议长期并行；不支持的连接应明确失败，不能出现成功连接却默默漏消息。回滚恢复成套程序与对应配置，保留期间已产生的事件和已读，不能恢复旧数据库覆盖新数据。

## 验收口径

不再由“2个Codex加1个Antigravity”直接推导固定MB/小时。需指定任务频率、正文大小、历史规模、在线时长、直连/中继及统计口径后测量。

- 固定场景采用一个Tray、Windows/WSL两个Bridge、2个Codex与1个Antigravity会话；其他来源是否活跃明确列出。真实3小时和后台8小时分别记录，任务结束时间不等于断网时间。
- 空闲稳定连接没有周期全量快照；每台含Tray和两个Bridge的应用层总量建议以不超过1MB/小时为预算目标，最终用测量验证。升级文件、模型API和浏览器业务流量单列，VPN封装/TCP重传与应用字节分开。
- 对固定任务脚本分别测每分钟6次、30次业务变化，以及长回答、未读积累、频繁工具事件。普通变化传输应接近“变化对象＋新增正文”的大小；增加大量不变历史会话不应令每次增量成比例膨胀。
- 通知优先及时交付，普通活动允许短时间合并；健康网络正常变更至界面更新的延迟目标建议不超过1秒，最终阈值以实际链路和用户要求确认。
- 故障矩阵覆盖短断网、超过恢复窗口、Hub/Relay/Tray重启、丢包、切换路径、慢客户端、客户端保存失败、重复事件及已读；恢复结果与权威状态一致，没有历史/已读丢失或无效保持唤醒。
- 补测正文首次获取与缓存命中、隐藏详情、关闭/恢复管理页、包下载续传；以实际收发字节、基准次数、增量次数和重连数作证，不只检查HTTP200。

预算仍须在目标网络验收，已有短时隔离实测及覆盖范围见开发记录。既往0.5GB账单仍取决于准确计数窗口；新实现的测试不能替代旧账单的逐请求证据。
