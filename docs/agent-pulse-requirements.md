# AgentPulse 需求文档

## 1. 项目目标与命名

构建一个面向个人开发者的多主机、多设备 Agent 会话状态与通知系统。用户可以集中查看不同主机上正在进行的 Agent 会话，并在任务结束、异常中止或需要用户参与时收到提醒。

- **系统名：** Agent 会话状态与通知系统
- **项目名：** AgentPulse
- **工程名：** `agent-pulse`
- **缩写：** `pls`

| 组件 | 名称 | 部署位置与职责 |
| --- | --- | --- |
| 主节点 | `agent-pulse-hub` | 内网 Docker 部署；保存会话、事件及已读状态，执行通知策略，提供 Web 管理界面 |
| 中继节点 | `agent-pulse-relay` | 公网 Docker 部署；轻量化暂存和转发消息，支持无法直连 Hub 的 Bridge 和 Tray，无 Web 界面 |
| Hook 服务 | `agent-pulse-bridge` | Agent 所在主机或运行环境；接收事件、内存暂存、重试和投递 |
| Agent 接入组件 | `xxx-adapter` | 对接具体 Agent 的 hook/plugin，转换为统一事件 |
| 桌面小组件 | `agent-pulse-tray` | 首版用户 Windows 桌面；托盘、会话列表、提醒、设备状态上报和已读同步，结构上保留 macOS/Linux 扩展能力 |

接入范围包含 OpenCode、Codex、Antigravity、ZCode 和 Qoder，但不是每个产品都覆盖每个平台。Linux 当前实施覆盖 OpenCode、Codex、Antigravity CLI 和 Qoder 中国版 CLI（`qoderclicn`）；本轮 Windows RC 只纳入 ZCode 图形界面；Windows Codex CLI 与 ChatGPT Windows 桌面端均列为后续规划，不在本轮实现或承诺支持。Qoder、Antigravity、OpenCode 的 Windows 终端适配不属于当前计划。ZCode 接入主会话开始、用户提交与正常完成，不推断工具事件或非正常退出。后续 Windows 来源优先考虑图形界面产品，ChatGPT Windows 桌面端等先调研公开接入能力，不预设存在 hook 或提前实现通用 GUI 采集平台。Codex 高级事件和物理多主机更新验收后续迭代，已有能力及待验证边界必须明确记录。

## 2. 部署与通信

- Hub 和 Relay 均通过 Docker 部署，提供镜像构建方式及 Docker Compose 示例；需要持久保存的服务端数据通过数据卷保留。
- GitHub Actions 自动检查、构建并发布 Hub/Relay 的 amd64、arm64 镜像；发布前执行容器恢复验证。模拟运行和目标架构真机验证分别记录。
- Hub 通过内网 `IP:端口` 访问，支持 HTTP/WebSocket 直连，不要求域名或内置 TLS；Web 管理界面使用同一访问入口。
- Relay 前置 Traefik 或 Nginx，负责域名入口和 TLS 终止；外部通过 HTTPS/WSS 访问，代理到容器可使用 HTTP。部署示例需覆盖长连接代理所需配置。
- Bridge 和 Tray 优先连接 Hub，连接失败后自动连接 Relay；Hub 恢复可达后自动回切，避免频繁切换。
- Hub 主动连接 Relay，拉取待处理事件、设备状态和已读回执，并通过该连接向 Relay 下发通知及状态更新。内网 Hub 无需向公网开放入站端口。
- Relay 为连接到它的 Tray 转发 Hub 生成的通知和状态更新，形成完整双向通路。
- Tray 使用 WebSocket 接收变化通知和上报设备状态，使用 HTTP 取得快照及提交已读回执。
- Hub 是会话、通知策略和用户级已读状态的权威来源。
- 若只是某台设备无法直连 Hub，但 Hub 与 Relay 仍连通，应保持完整功能。
- 若 Hub 本身宕机或完全断网，Bridge、Relay 和 Tray 缓存待处理数据；新的通知决策和手机推送延迟到 Hub 恢复。当前版本不要求 Relay 接管 Hub 的决策职责。

Bridge 的运行方式：

- Windows 原生环境支持将 Bridge 随 Tray 集成分发并管理启停，便于统一安装和服务管理；采用 Tray 内置 Go Bridge 并管理其辅助进程的方式。
- Windows 面向用户只提供 Tray 入口，不要求用户运行 Hub、Relay、测试客户端或发布工具；本机 Agent 接入能力由 Tray 统一提供和管理。启用本机接入时允许存在内部 Go 辅助进程。
- Linux 下使用用户级 systemd 服务管理 Bridge，提供安装、启动、停止和查看状态的说明。WSL2 在启用 systemd 的环境中采用相同方式。
- Bridge 同时无法连接 Hub 和 Relay 时，仅在内存中暂存事件，重连后补发，无需写入磁盘。Bridge 进程退出、崩溃或随 Tray 退出时，尚未发送的事件丢失可以接受。

## 3. Agent 接入与会话管理

### 3.1 接入要求

- 优先通过各 Agent 官方 hook/plugin 接入，并核实目标版本及 CLI、IDE 等形态的实际能力。
- adapter 只负责获取和转换事件；本地接入由 Bridge 统一负责投递、缓存和重试。
- hook 应快速返回，通知网络故障不能长时间阻塞 Agent，也不能代替用户批准操作。
- Windows 原生、WSL2 和 Linux 中的 Agent 均可接入。Bridge 跟随 Agent 的运行环境部署，同一电脑的 Windows 和 WSL 实例可分别标识。
- 安装或更新接入配置时，保留用户已有的其他 hook/plugin 配置。
- 扩展性需考虑只能提供 webhook 或简单 JS 的云端 Agent：允许经 HTTP 向可达的 Hub/Relay 提交统一事件，或通过薄接入层转换，不强制部署 Bridge。统一事件不得依赖本地进程或文件路径；当前不要求交付具体云端适配器或独立网关服务。

### 宿主版本兼容原则

对于 `x.y.z` 数字版本，`x` 是主版本、`y` 是次版本、`z` 是补丁版本。以已验收版本线为基准：同一 `x.y` 下补丁版本变化默认支持，不要求逐个补丁验收；同一 `x` 下次版本变化允许继续使用，但不承诺兼容性；主版本变化需要重新测试后再纳入支持。默认支持是项目的兼容政策，不是第三方不会破坏接口的保证，已知不兼容情况须明确说明。

### 3.2 会话与事件

支持观察会话开始、恢复、运行、等待用户、结束及失联等状态。需要提醒的事件包括：

- 本轮处理结束或明确的任务完成；
- 执行失败、异常中止或用户主动中断；
- 等待用户回答；
- 等待用户批准或权限确认。

区分“本轮结束”“任务完成”“会话关闭”和“工具调用失败”，不能简单视为同一种完成或失败。开始、恢复和运行状态用于维护会话列表，默认不产生强提醒。

各 Agent 的正常用法是直接启动；安装 hook 后必须沿用原命令采集，不额外要求 Bridge 包装启动。ACP 方式启动在本项目中视为子代理运行，其事件不推送给用户。过滤可在 hook、Bridge 或 Hub 中实现；应复用本机公共接入能力，减少多种 Agent 及新增来源的重复开发。

只纳入面向用户的主代理会话。adapter 应根据原生父子会话关系或 Agent 身份排除子代理的消息及生命周期事件，不产生子代理独立会话条目、桌面提醒或手机推送；主代理汇总子代理结果后产生的自身事件仍正常处理。无法可靠识别子代理的接入形态需要明确说明限制。

事件应能识别来源主机、运行环境、Agent、会话、事件类型和发生时间，并包含可展示的标题和内容。具备条件时附带项目名称及会话标题。

维护所有已接入、可观察的进行中会话；组件重启或重连后恢复并核对状态。进程崩溃、强制结束或主机断电可能无法触发 hook，需要结合进程状态或心跳辅助检测；无法确定原因时显示“失联／未知”。

五个 adapter 按上述平台分工属于交付范围，不要求五个产品都具备 Windows 终端适配。各自需说明支持的版本、事件和限制；缺少原生事件时，采用可靠的替代检测，或明确标注能力缺口，不根据猜测报告成功或失败。

### 会话身份与名称

- 所有已接入来源以原生会话 ID 定位主会话，Hub 主键为来源主机、Agent、会话 ID。改名、继续任务和恢复不会产生新会话。
- 会话 ID 仅在后台传输、存储和查询使用，不在 Web、Tray、托盘菜单、详情、提醒或缺省标题中展示。
- 展示名称跟随 Agent 的最新名称，与项目名独立；原生名称未获取时显示“未命名会话”，不拿项目名、ID 或首条提示词填充。
- 改名作为独立名称元数据同步，没有改名事件时等待下一次真实事件，不改变运行/等待状态、人工状态、归档、已读或未读，不生成完成/手机提醒。
- 原生改名事件优先；缺少改名事件时随下一次真实事件读取可靠名称元数据。没有可靠来源的 Agent 明确标为未完成改名接入，不猜测字段或从正文生成名称。
- 本项目的会话别名只作辅助备注，不覆盖 Agent 的最新会话名。
- 用户首次明确要求前，不实现通讯或存储的旧版兼容，包括旧字段回退、接收器版本门槛和数据库迁移；候选统一使用当前结构，结构变化可显式重建测试数据。实际服务器清空或重建仍须部署者授权。

### 3.3 Hub Web 管理界面

Hub 提供简洁的 Web 管理界面，实时展示：

- 已连接 Bridge 的主机、运行环境、连接状态和最近心跳；
- 已连接 Tray 的设备、连接状态、锁屏及全屏状态；
- 当前进行中的主代理会话及其 Agent 类型、所属主机、标题和状态。
- 各主机 Adapter 的目标版本、已安装版本、生效情况和更新失败原因。

覆盖直连 Hub 和经 Relay 接入的实例，能够区分连接路径；连接状态变化应及时更新，不能把过期信息显示为实时在线。Relay 保持轻量化，不提供管理界面。

### 3.4 Adapter 独立更新

- Adapter 与 Bridge 分别发布，产品专属事件映射和接入修复不得要求每台主机重新部署 Bridge；通用协议或基础运行能力修改时一并更新本项目相关组件，开发阶段不维护旧接收器支持。
- Bridge 初次安装后，可从配置的 Hub 自动检查并获取兼容适配包；离线主机恢复连接后补更新，经 Relay 连接的主机也能获取。新 Agent 在本机受管理范围内且已安装时可自动接入。
- 本地 hook 使用稳定入口，包切换不修改调用路径。更新保留用户已有 hook/plugin 配置，校验失败继续使用旧版本，并支持集中指定版本、单机固定版本和回滚。
- 只执行可信发布者的适配包；包的来源、内容摘要及 当前格式、Agent 版本政策及目标平台均须校验。免登录的 Web 管理页不得发布可执行代码。
- Hub 展示目标版本、已安装版本、实际生效版本和失败原因。原生插件只能在 Agent 重新加载或重启后生效时明确标记，不声称任意插件均可热更新，也不强行中断用户的 Agent。

## 4. 通知规则

同一用户的所有在线 Tray 均同步事件，是否立即展示由桌面状态决定。

| 设备情况 | 桌面行为 | 手机行为 |
| --- | --- | --- |
| 至少一台在线且未锁屏 | 所有在线且未锁屏客户端展示；锁屏客户端缓存 | 默认不推送 |
| 在线客户端全部锁屏 | 接收并缓存，解锁后展示 | 推送标题及精简内容 |
| 没有在线客户端 | 服务端保存，重连后补发 | 推送标题及精简内容 |
| 未锁屏但处于全屏状态 | 小型提醒标识，退出全屏或点击后完整展示 | 默认不因全屏而推送 |

- 设备在线状态依据有效心跳判断，休眠、断网或过期状态不能一直视为在线。
- 手机渠道优先复用已有推送服务，以配置 GET/POST 请求、URL、headers 和标题/正文参数为主；特殊签名或业务响应只做局部适配，不建设通用插件/工作流平台。首版至少接通一种用户实际使用的渠道，并记录配置方式，不要求自建服务。
- 手机渠道可独立配置标题和正文的字符上限，默认不限制；超长时仅截短该渠道的发送文本并标明省略，保留 Hub 和桌面的完整事件，不固定第三方渠道的专有阈值。
- 当前先接通已有渠道，密钥通过环境变量或仓库外私有配置提供，不进入版本控制。多渠道优先级与失败切换后续迭代；不能把配置顺序解释为已实现的优先级。
- 手机只发送适合提醒的摘要，避免直接发送完整会话或大量内容。
- 通知和手机推送需要去重；发送失败可重试，且不能阻塞 Agent。
- 对已读或已失效的历史提醒，恢复连接后不再重复弹出。

## 5. 桌面小组件交互（首版 Windows）

Tray 定位为小型桌面组件，同时允许以此尝试 GPUI。界面、连接/状态逻辑及平台系统调用保持边界；通过小型原型验证首选路线，不以框架热度或 GPU 绘制速度代替常驻资源与桌面交互验证。未来 macOS/Linux 仅考虑扩展性，当前无需提前实现。

技术首选 Rust + GPUI，通过小型原型验证后继续使用 Rust；GPUI 确认不可行时采用 Go + Walk。Tray 不采用浏览器或 WebView 页面方案，不以打开 Hub Web 替代本地提醒、会话列表和已读交互。

- 默认隐藏主窗口并驻留系统托盘，支持登录自启动、打开列表和退出；应用需要防止重复启动形成多个实例，不能仅通过相同状态文件的写锁代替应用实例控制。
- 开发演示同样默认驻留托盘，显式参数才打开列表或设置。免安装运行时配置与数据随程序目录保存，默认读取旁边的 `tray.yaml` 和 `data/`，不依赖启动工作目录。
- 登录自启动通过当前用户“启动”文件夹的 `AgentPulse.lnk` 维护，状态以快捷方式和 Windows 禁用状态为准，不依赖本地配置布尔值；用户可自行删除快捷方式。移动程序后识别旧位置并允许更新或移除，不写注册表、不绕过系统禁用。
- 设置和详情使用原生标题栏并移除重复关闭按钮；详情允许缩放和最大化、长消息内部滚动，设置允许缩放但不最大化；悬浮、列表小窗、提醒继续无框。
- 托盘图标右键打开类似 ChatGPT 桌面端形式的上下文菜单，以菜单项展示活跃会话及状态，并提供悬浮图标的显示/隐藏操作；右键本身不打开会话小窗主界面。点击悬浮图标或明确选择菜单里的“打开会话列表”才打开无框小窗。
- 右键菜单保持紧凑，会话区仅展示活跃会话，限定标题显示字数，不展示主机；状态与未读仅保留一种会话提示。当前设计推荐保留状态，未读由托盘角标和会话小窗继续呈现；尺寸、条数及字数上限见桌面设计。
- 用户可在屏幕右下角放置置顶悬浮图标，支持拖动和贴边收起；收起后保留少量可见部分，鼠标移入时滑回屏幕范围，移开后再次收起。
- 点击悬浮图标打开无框会话小窗，显示会话标题、主机、环境、Agent、会话状态，以及需要用户关注的未读标识。小窗与悬浮入口在多屏和缩放变化后仍可找到、可操作。
- 点击具体会话后才打开较大窗口显示该会话相关内容；不会因为收到事件就自动展开大窗口。事件按时间线排列，显示类型和阅读状态，最新一条默认展开，点击其他条目展开内容。
- 会话管理需考虑归档/恢复、已读及异常状态修正；具体交互与状态语义先设计确认，来源状态和人工操作不能混淆。
- 未锁屏且非全屏时，悬浮图标关闭则发送 Windows 系统通知；贴边收起则露出并短时强调；已经显示则短时强调图标。主动提醒不抢焦点，允许按来源静默并保留记录与未读。
- 可绑定一个或多个来源主机，只在其在线且有运行任务时保持 Windows 系统唤醒，结束、等待或失联后释放，不改变电源计划或强制屏幕常亮。
- Tray 可首次直连 Hub 自动取得中继信息并缓存，手动配置优先；Windows 程序文件、窗口和托盘均提供一致图标。
- 用户解锁后，先同步最新未读状态，再集中展示仍未读的事件；大量积压时合并展示。
- 没有未读事件时，提醒窗口取消置顶；用户启用的悬浮入口仍保持置顶可达。
- 全屏时使用遮挡区域较小的提醒标识；点击标识或退出全屏后展示完整内容。
- 对无法可靠覆盖的独占全屏等场景，允许延迟到退出全屏后展示，不能强制打断全屏活动。
- Tray 上报连接、锁屏、解锁及全屏状态，断线时保留必要缓存。
- Tray 运行在 Windows 用户交互会话中，不能依赖 Windows Service 直接显示桌面界面。
- 演示仅存在于开发构建；使用 `--demo` 时以前台控制台模式运行并输出日志。发布构建排除演示代码、数据、控件与启动入口。

已确认的交互布局、默认值、单实例范围和 GPUI 可行性见 [Windows 桌面设计](windows-desktop-design.md)。实施进度与验收证据单独记录在开发记录，不能以设计预览代替原生验收。

## 6. 已读同步与可靠性

- 已读属于用户级状态：任意一台 Tray 阅读或明确标记事件后，所有客户端清除对应未读。
- “已送达”“已展示”和“已读”分开处理；仅弹出窗口或解锁不自动算已读。
- 已读不会删除正在进行的会话；已读事件可保留在历史中。
- 离线时的已读操作需要缓存，重连后同步；网络分区期间允许短暂不一致，恢复后收敛。
- 事件具有稳定唯一标识，重试、直连与中继切换不得造成重复提醒。
- Hub、Relay 和 Tray 重启后，应恢复各自已持久化的事件、未读和待同步状态。Bridge 仅使用内存队列，不要求重启恢复；尚未离开 Bridge 内存的事件不在持久化保证范围内。
- 可信内网的个人 Hub/Web 默认允许免登录；需要时使用共享令牌或既有反向代理认证，不建设账号、角色、多租户或凭据生命周期系统。公网 Relay 必须保留简单的共享令牌等访问控制，TLS 不能代替调用方鉴权。
- Relay 公网通信由前置代理提供 TLS；Hub 内网直连允许 HTTP。配置中的令牌可用用户级文件或环境变量保存，不强制依赖 Windows 凭据库或自定义本地加密。密钥不写入仓库，日志避免记录敏感内容；保留基本日志和连接诊断。

## 7. 技术方向、架构支持与开发安排

采用单仓库 `agent-pulse`，组件可分别构建和部署。以下为已确认的技术方向，不规定具体数据库、接口路径和内部模块实现。

| 部分 | 技术方向 | 目标运行环境 |
| --- | --- | --- |
| Hub、Relay、Bridge | Go | Hub、Relay 部署 Linux Docker；Bridge 支持 Windows、WSL2、Linux |
| Hub Web 界面 | Vue 3 + TypeScript + Vite | 随 Hub 镜像交付，通过浏览器访问 |
| Tray | 首选 Rust + GPUI，验证不可行时使用 Go + Walk | 首版 Windows，保留 macOS/Linux 扩展边界 |
| OpenCode adapter | TypeScript | OpenCode 所在环境 |
| 其他 adapter | 独立 Go 命令包和声明式 hook 配置调用 Bridge；未来云端可直接提交 HTTP 事件 | 对应 Agent 所在环境 |

多语言单仓库的根目录负责工程组织，Go module 放在 `go/`；Web、Tray 和适配器可独立构建。Node.js 环境统一使用 Volta，包管理统一使用 pnpm。避免为未确定的技术栈提前安装完整开发环境。

人工配置使用 YAML，提供注释清晰的示例和严格字段/类型校验；敏感值支持显式环境变量引用。网络协议和程序状态文件的格式独立于人工配置，不要求统一成 YAML。

Bridge 首版保持 Go。若 GPUI 可行且后续对 Bridge 的同功能、同负载发布构建测量表明 Rust 有实际资源收益，可再评估迁移；不从 Tray 的资源表现推断 Bridge 收益，不提前重写。迁移不得破坏稳定入口、事件协议及 Adapter 独立更新能力。

### 7.1 架构支持

- Hub、Relay、Bridge 支持 `amd64` 和 `aarch64`，构建工具及 Docker 中通常将后者标记为 `arm64`。
- Hub 和 Relay 提供 `linux/amd64`、`linux/arm64` 镜像。
- Bridge 提供所支持操作系统的两种架构构建产物；Windows ARM64 可独立运行 Bridge，不要求提供 ARM64 Tray。
- Tray 只要求 Windows `amd64`，其集成的 Bridge 使用相同架构。

### 7.2 开发顺序

**先在可持续运行的 Linux 开发主机上完成大多数工作，再在 Windows 开机后继续剩余任务和 Tray 开发。** Windows 暂时不可用不应阻塞可独立完成的 Linux 工作。

1. **Linux 阶段：** 完成 Hub、Relay、Bridge、Hub Web 界面、Docker 部署、多架构构建、用户级 systemd 配置、Linux 可运行的 adapter、手机推送及协议和可靠性测试。通过测试客户端验证通知、设备状态和已读同步链路，为 Tray 准备可联调接口。
2. **Windows 阶段：** 在 Windows 原生环境及 WSL2 中继续开发，完成 Tray、Windows Bridge 集成与管理、Windows 专属 adapter 验证、安装分发和整体联调。
3. **原生验收：** 托盘、置顶、焦点、锁屏、解锁、全屏、多显示器及安装行为必须在实际 Windows 用户会话中验证。Linux/WSL2 的构建及模拟测试不能替代这些验收。

提供 Linux/WSL2 服务启动、测试和构建脚本；Windows 阶段补齐调用 Windows 工具链构建、启动和打包 Tray 的脚本。可以从 WSL2 调用宿主机工具链，无需将全部开发迁移到 Windows 原生终端。

持续维护已完成事项、可复现命令和待完成清单，方便在两台开发主机之间通过 Git 接续工作。缺少某个 Agent、目标架构运行环境或手机渠道凭据时，如实记录待验证项，不能将模拟或交叉编译结果当作真实运行验收。

需求、设计和运行说明仅描述现行规则；修改历史集中维护在独立变更记录，实施状态和验证证据放在开发记录，不在正式正文中穿插修订说明。

## 8. 交付与验收

交付全部组件及 Hub Web 界面源码、五个 adapter、Docker 部署和代理配置示例、用户级 systemd 配置、多架构构建方式、安装运行说明和相关自动化测试。可以分阶段实施，但 Linux 阶段或最小闭环完成不代表全部开发完成。

主要验收场景：

1. 各 adapter 在其支持的事件范围内真实触发事件，Tray 能显示正确的主机、会话、标题和内容。
2. Hub Web 界面实时展示直连及经 Relay 接入的 Bridge、Tray 和进行中的主代理会话，状态变化及重连后列表正确。
3. 设备无法直连 Hub 时，经 Relay 仍可接收通知、上报设备状态及同步已读。
4. Hub 不可达时事件可由 Relay 暂存；Hub、Relay 均不可达时，Bridge 在进程存活期间以内存暂存并在重连后补发，进程退出后允许丢失该部分事件。
5. 两台 Tray 同时在线，一台标记已读后另一台同步消除未读；离线设备重连后也保持一致。
6. 全部客户端锁屏或离线时，手机收到标题和精简内容；Windows 解锁后展示尚未读的积压事件。
7. 全屏时不强制弹出大窗口，点击标识或退出全屏后按用户交互展示提醒；无未读时提醒窗口取消置顶，用户启用的悬浮入口仍保持可达。
8. 重试、网络切换和组件重启不会丢失已持久化事件或造成重复提醒；不要求恢复 Bridge 进程退出前未发送的内存事件。
9. 子代理消息及生命周期事件不进入独立会话列表或触发通知，主代理自身事件正常处理。
10. Hub 的 IP:端口访问和 Relay 经 Traefik/Nginx 的域名、TLS、长连接代理均可用；目标架构构建产物齐全，记录各架构实际运行验证情况。
11. Linux 用户级 systemd 能管理 Bridge；Windows Tray 能管理集成的 Bridge；Linux 开发流程不依赖 Windows 持续开机。
12. Windows 原生客户端验收完成；交付说明如实列明各阶段进度、已验证环境及已知限制。
13. 两台以上主机保持相同 Bridge 可执行版本，仅发布 Adapter 包即可完成接入更新；覆盖离线补更新、中继下载、兼容性拒绝、配置保留、失败回滚及常驻插件待重新加载的状态。

## 9. 范围边界

当前目标是单用户、多主机、多 Windows 客户端。不要求远程控制 Agent、从通知中回答问题或批准权限、同步完整会话和源代码、多租户后台、Hub 高可用集群或手机专用客户端。macOS/Linux Tray 与云端 webhook/JS 接入当前只要求保留合理边界，不属于首版必须实现的功能。
